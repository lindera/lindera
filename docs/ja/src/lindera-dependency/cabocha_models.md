# CaboCha のモデル

[CaboCha](https://taku910.github.io/cabocha/) には、京都大学テキストコーパス 4.0 で学習したモデルが付属しています。コーパスが無いと学習し直せません。また、文節の基準は京大コーパスのもので、このクレートのモデルが従う UD Japanese-GSD のものとは違います。`lindera dependency convert-cabocha` は、そのモデルを[モデルファイル](./model_file.md)に変換します。変換したモデルでの解析は、CaboCha の解析と同じ結果になります。

## モデルの利用条件

**変換したモデルの利用は、元のモデルと同じく、研究目的と個人利用に限られます。ご自身が入手した CaboCha のファイルを変換し、結果を配布しないでください。** このクレートとそのリリース、ビルドは、CaboCha のモデルを含みません。

CaboCha のライセンス（LGPL または BSD ライセンス）は、モデルには及びません。CaboCha の配布ページには、次のように書かれています。

> 付属のモデルファイル(model 以下のファイル)にはBSDライセンス は適用されません。BSDライセンス は, 付属のプログラムや学習ツールのソース・コード, ドキュメントのみに適用されます。
>
> 付属のモデルファイルは, 株式会社毎日新聞社の御厚意により 配布されている毎日新聞記事CD-ROM版を基に学習, 作成されたものです。付属のモデルファイルは, 毎日新聞データ使用許諾に関する覚書に記載の利用条件内で その使用及び, 複製，改変，頒布が認められます. そのため配布しているモデルをそのままの形で使うことは, 研究目的, 個人利用に限られます.

つまり、BSD ライセンスが及ぶのは、プログラム、学習ツール、ドキュメントだけです。モデルは毎日新聞記事 CD-ROM 版から作られたもので、そのデータの使用許諾の覚書の条件の範囲で、使用・複製・改変・頒布が認められます。そのため、配布のモデルをそのまま使うことは、研究目的と個人利用に限られます。ご自身のコーパスで学習したモデルには、この制限はありません。学習の方法は、[文節の区切り](./chunking.md)と[係り受けの解析](./parsing.md)を見てください。

## 対応するモデル

| CaboCha のモデル | ファイル | |
| --- | --- | --- |
| IPA | `chunk.ipa.txt`、`dep.ipa.txt` | 変換できます。辞書 `ipadic` 用のモデルになります |
| JUMAN | `chunk.juman.txt`、`dep.juman.txt` | 変換できます。辞書 `jumandic`（[JUMAN 辞書](../lindera-jumandic.md)）用のモデルになります |
| UniDic | `chunk.unidic.txt`、`dep.unidic.txt` | 変換できます。辞書 `unidic` 用のモデルになります。`--dictionary` で、`unidic-cwj` か `unidic-csj` 用にもできます |
| 固有表現 | `ne.*.txt` | 変換しません |

ファイルは、CaboCha のソースの `model/` にあるテキスト形式のモデルで、UTF-8 のものです。インストール先にあるコンパイル済みのモデル（`dep.ipa.model`）は読みません。マシンに依存する形式のためです。

2 つのファイルは、同じモデルのものを渡してください。品詞体系は、解析器のモデルのヘッダー（`posset: IPA`）から読みます。区切りのモデルには、どの体系のものかが書かれていません。`chunk.ipa.txt` と `dep.juman.txt` を渡すと、エラーにならずに、文節を誤って区切るモデルができます。

## 変換

コマンドは、`lindera` の既定のビルドにあります（既定のビルドは `train` の feature を持ちます）。

```sh
cargo install lindera-cli --features embed-ipadic
```

```sh
lindera dependency convert-cabocha \
    --chunker cabocha/model/chunk.ipa.txt \
    --parser cabocha/model/dep.ipa.txt \
    --output cabocha-ipa.model
```

## 変換するもの

**区切りのモデル**は、CRF++ のテキスト形式のモデルです。テンプレート、素性の文字列、重みを、そのまま区切りの部分に入れます。重みは 32 ビットの浮動小数点に丸めます。CaboCha が読むコンパイル済みのモデルで、CRF++ がそう持つためです。

**解析器のモデル**は、2 次のカーネルの support vector です。判定の点数は、support vector についての和 `Σ α (1 + s)^2` で、`s` は support vector が判定と共有する素性の数です。これは、バイアス、素性ごとの重み、素性の対ごとの重みに、誤差なく展開できます。解析器の部分が持つのは、この形です。ただし、CaboCha はそのままでは解析しません。`cabocha-model-index` がテキストのモデルをコンパイルするときに近似します。変換は同じ手順を踏むので、判定で足し合わせる整数が CaboCha と同じになります。

- 頻度の高い 3,000 個の素性どうしの対は、すべて残します。
- それ以外の対は、2 件以上の support vector に現れ、重みが `sigma × positives / all` 以上か、`-sigma × negatives / all` 以下のときに残します。`sigma` は 0.0001 です。positives と negatives は、重みが正の support vector と負の support vector の件数、all は全件数です。
- 重みは 32 ビットの浮動小数点で足し込み、絶対値の最大を 1,048,575 で割った値で割って、整数に切り捨てます。モデルファイルは、その整数を量子化せずに持ち、割った値を重みのスケールとして持ちます。

| オプション | 既定 | |
| --- | --- | --- |
| `--sigma` | 0.0001 | `cabocha-model-index` の `-s` |
| `--min-support` | 2 | `-n` |
| `--frequent-features` | 3000 | `-F` |

既定は `cabocha-model-index` の既定で、CaboCha 自身のビルドは、これで付属のモデルをコンパイルします。`--sigma 0 --min-support 1` はすべての対を残します。これはカーネルそのもので、CaboCha が解析に使うものではありません。

| モデル | | 残る対 | 重みのある対 | ファイル | 変換の時間 |
| --- | --- | --- | --- | --- | --- |
| IPA | 既定 | 10,141,653 のうち 3,727,492 | 3,713,127 | 51.8 MB | 3.6 秒 |
| IPA | `--sigma 0 --min-support 1` | 10,141,653 | 9,988,000 | 102.0 MB | 4.5 秒 |
| JUMAN | 既定 | 10,578,633 のうち 3,687,535 | 3,676,410 | 52.0 MB | 4.0 秒 |
| JUMAN | `--sigma 0 --min-support 1` | 10,578,633 | 10,450,076 | 106.2 MB | 4.9 秒 |
| UniDic | 既定 | 8,881,051 のうち 3,360,320 | 3,350,964 | 47.7 MB | 3.0 秒 |
| UniDic | `--sigma 0 --min-support 1` | 8,881,051 | 8,782,456 | 91.2 MB | 3.7 秒 |

**素性を作るもの**は、モデルファイルのデータです。変換したモデルでは、CaboCha のものになります。

- 表層は、素性にする前と、記号として照合する前に、CaboCha の表で正規化します。半角カナは全角に、全角の英字・数字・記号は ASCII になります（`ＡＢＣ` は `ABC`、`ｶﾞ` は `ガ`）。
- IPA では、機能語は、助詞、助動詞、動詞,非自立、動詞,接尾、形容詞,非自立、形容詞,接尾です。主辞は、そのどれでもなく記号でもない、最後の形態素です。このクレートの `ipadic` のスキーマとは違います。そちらはパターンが多く（[主辞と機能語](./head_and_function_word.md)）、利用 / し / た の主辞は、ここでは し、そちらでは 利用 です。
- JUMAN では、機能語は、特殊でない最後の形態素です。主辞は、特殊・助詞・接尾辞のどれでもない最後の形態素です。2 つは別々に決めます。規則の形が IPA とは違い（[主辞と機能語](./head_and_function_word.md#規則)）、名詞 1 語の文節では、その名詞が両方になります。品詞は 2 段で、活用形は 4 列目です。
- UniDic では、機能語は、助詞、助動詞、接尾辞,形容詞的、接尾辞,形状詞的、接尾辞,動詞的です。主辞は、そのどれでもなく、空白・補助記号・記号でもない、最後の形態素です。CaboCha は、品詞の段数を区切りと解析器で変えて読みます。区切りは 4 段で、解析器は 2 段と、その次の次の列を活用形として読みます。UniDic では、その列は品詞の 4 段目（モデルでは 一般・名・国・姓）で、活用形ではありません。モデルはこの読み方で学習されているので、同じ読み方をしたときだけ、CaboCha と同じ解析になります。そのため、スキーマは品詞を 4 段、活用形を 4 列目とし、解析器の素性の集合を 2 段に限ります（`pos-levels=2`。[係り受け解析](./parsing.md#素性の集合)を参照）。
- 句読点は `。` と `、`、括弧は CaboCha のもので、どれも表層の全体で照合します。

## CaboCha との一致

`scripts/dependency/cabocha_models.sh` は、IPA のモデル（`--posset juman` か `--posset unidic` を付けると、JUMAN か UniDic のモデル）を変換し、同じ入力を、CaboCha 0.69（96e100a。`scripts/dependency/build_baselines.sh` でビルドし、モデルは CaboCha 自身のビルドがコンパイルしたもの）と、変換したモデルを使う `lindera dependency parse` に渡します。入力は、UD Japanese-GSD と UD Japanese-PUD の 9,066 文です。決まったテキストとして使うだけで、その正解は使いません。

同じ形態素（Lindera と IPADIC のもの）を渡すと、すべてが一致します。

| ファイル | 文節が同じ文 | 係り先が同じ文節 | 主辞と機能語が同じ文節 |
| --- | --- | --- | --- |
| GSD dev | 100%（506 / 506） | 100%（3,740 / 3,740） | 100%（4,246 / 4,246） |
| GSD test | 100%（542 / 542） | 100%（4,059 / 4,059） | 100%（4,601 / 4,601） |
| PUD | 100%（994 / 994） | 100%（9,076 / 9,076） | 100%（10,070 / 10,070） |
| GSD train | 100%（7,024 / 7,024） | 100%（50,718 / 50,718） | 100%（57,742 / 57,742） |

判定の点数も、CaboCha が書く小数 6 桁まで同じです。

`--sigma 0 --min-support 1` では、文節は同じで、係り先は 99.65%〜99.79% が同じです（3,727 / 3,740、4,048 / 4,059、9,057 / 9,076、50,573 / 50,718）。CaboCha の近似は、係り先を約 360 個に 1 個の割合で変えます（67,593 のうち 188）。

テキストからの場合、CaboCha は MeCab と mecab-ipadic で、`parse` は Lindera とその IPADIC（mecab-ipadic のソースから作ったもの）で形態素にします。2 つの形態素が同じになる文は 91%〜98% で、その文の解析は同じです。

| ファイル | 形態素が同じ文 | そのうち解析が同じ文 |
| --- | --- | --- |
| GSD dev | 97.04%（491 / 506） | 100%（491 / 491） |
| GSD test | 98.15%（532 / 542） | 100%（532 / 532） |
| PUD | 91.15%（906 / 994） | 100%（906 / 906） |
| GSD train | 96.48%（6,777 / 7,024） | 100%（6,777 / 6,777） |

残りの文は、形態素の切り方が違います。そのほとんどは、辞書に無いカタカナの語のところです（PUD と GSD train で 335 文のうち 332 文）。MeCab は `コリ・シューマン` を 1 語にし、Lindera は 3 語にします。MeCab が `メトロ` / `ポリ` / `タン` と切るところを、Lindera は `メトロポリタン` にします。これはトークナイザーの違いで、モデルの違いではありません。

### JUMAN のモデルでの一致

入力は、同じファイルの 9,100 文で、形態素は MeCab と mecab-jumandic のものです。すべてが一致します。

| ファイル | 文節が同じ文 | 係り先が同じ文節 | 主辞と機能語が同じ文節 |

| GSD dev | 100%（507 / 507） | 100%（3,870 / 3,870） | 100%（4,377 / 4,377） |
| GSD test | 100%（543 / 543） | 100%（4,194 / 4,194） | 100%（4,737 / 4,737） |
| PUD | 100%（1,000 / 1,000） | 100%（9,430 / 9,430） | 100%（10,430 / 10,430） |

点数も、ここでも小数 6 桁まで同じです。`--sigma 0 --min-support 1` では、文節は同じで、係り先は 99.63%〜99.77% が同じです（3,861 / 3,870、4,181 / 4,194、9,395 / 9,430、52,648 / 52,811）。係り先が変わるのは 320 個に 1 個です（70,305 のうち 220）。

テキストからの場合、CaboCha は MeCab と mecab-jumandic で、Lindera は同じソースから作った JUMAN 辞書で形態素にします（`lindera tokenize` の形態素を `parse` に渡します）。モデルが読む 5 列では、ほぼすべての文で形態素が同じになり、その文の解析は同じです。

| GSD dev | 99.61%（505 / 507） | 100%（505 / 505） |
| GSD test | 99.63%（541 / 543） | 100%（541 / 541） |
| PUD | 100%（1,000 / 1,000） | 100%（1,000 / 1,000） |
| GSD train | 99.79%（7,035 / 7,050） | 100%（7,035 / 7,035） |

残りの 19 文は、形態素の切り方が違います。そのうち 17 文は、数字の間の `・` のところで、`lindera tokenize --disable-break-characters` なら MeCab と同じに読みます（[使用例](../lindera-jumandic/examples.md#mecab-との一致)）。

## 制限

- **速さ**。GSD train の 7,024 文を形態素から解析するのに、`parse` は 3.03 秒、CaboCha は 0.92 秒かかります。ほかの 2 つのモデルも、これより遅くはありません。この 2 つが 2.98 秒と 0.87 秒かかった回に、JUMAN のモデルは 7,050 文に 2.60 秒（CaboCha は 0.77 秒）、UniDic のモデルは 7,024 文に 2.60 秒（CaboCha は 0.77 秒）でした。変換したモデルは、対ごとに重みを持ちます。このクレートのモデルは、対を表にハッシュします。そちらの速さは[モデルファイル](./model_file.md)を見てください。
- **最後の文節への係りの点数**は 0 です。このクレートのどのモデルでも同じです。
- **長い文節**。CaboCha は、1 つの文節について、素性を 128 個、素性の文字列を 2,048 バイトまでしか持ちません。このクレートはすべて持ちます。上のテキストの 76,659 文節は、最大でも 40 個・882 バイトで、mecab-jumandic の形態素の 79,405 文節は、最大でも 42 個・818 バイト、`unidic` の形態素の 78,714 文節は、最大でも 40 個・953 バイトで、上限に届きません。上限を超える文節では、結果が違いえます。
- **区切り**。このクレートは、`B` で始まる最良の経路を探します。CaboCha は、最良の経路を取ってから、最初の形態素を文節の始まりにします。また、CRF++ は 1 つの形態素の重みを 32 ビットの浮動小数点で足し、このクレートは 64 ビットで足します。どちらも、上のテキストの文節を変えませんでした。
- **精度**。CaboCha のモデルの精度は、ここでは測っていません。京大コーパスが手元に無く、UD Japanese-GSD での精度は、文節の 2 つの基準を比べることになるためです。
- **未検証**: Linux（x86_64）の GCC 15.2 以外のコンパイラ・OS でビルドした CaboCha。
