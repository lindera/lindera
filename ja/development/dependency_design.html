設計メモ: 係り受け解析

日本語の文節の係り受け解析を行うクレート lindera-dependency（#1417）の設計メモです。何を決めたか、なぜそう決めたか、参照した実装が何をしているか、決定の根拠になった数字と、その数字をもう一度出す方法を記録します。

このクレートは、Lindera 7.1.0 から公開しています。使い方は Lindera Dependency の章とクレートの README にあります。このページは、クレートを変更する人のためのものです。

このページを更新する人: 決定や数字を変える pull request が、このページも英語と日本語の両方で直します。

目的

係り受け解析は、文の形態素を文節にまとめ、文節ごとに、その文節が係る先の文節を求めます。

彼は 本を 読んだ。
彼は ──────┐
本を ──────┤
読んだ。 ◀──┘   (root)

定評のあるツールの CaboCha と J.DepP は、C++ で書かれていて、MeCab の出力の上で動きます。lindera-dependency は同じことを Rust で、Lindera のトークンか、任意の形態素の列に対して行います。

想定する使い道は、最後の 1 ポイントの精度よりも、速さと組み込みやすさが効くものです。検索のために文節の対を索引に入れる、検索用のコーパスやナレッジベースのために（主語、目的語、述語）の三つ組を取り出す、規則による照合、などです。

最初のリリースに入れないもの: 固有表現、述語項構造、並列の種類、ニューラルモデル。韓国語は、日本語のモデルを出した後に、要望があれば検討します。中国語は対象外です。

決定

各決定には、それを決めた Issue を添えます。決定を変えるときは、その pull request がこの表も直します。

決定理由Issue
クレートは lindera-dependency で、この workspace のメンバーにする。文節の区切り、係り受け解析、後の固有表現は、この 1 つのクレートに置く。Lindera は、バインディング・コマンド・ドキュメントを 1 つのリポジトリに置いている。モデルのリリースの周期の違いは、クレートではなくモデルのファイルで吸収する。#1417
コアは形態素の列（表層と素性の列）を受け取り、トークナイザに依存しない。Lindera の外の型も解析でき、既定のビルドは依存がなく、wasm32-unknown-unknown 向けにビルドできる。#1417、#1418
このクレートが依存するのは、feature の裏の lindera-segmenter まで。lindera と lindera-analysis には依存しない。トークンフィルターのために lindera-analysis がこのクレートに依存する。逆向きの依存もあると循環する。#1419
文節は UD Japanese-GSD のもの（国語研の基準。BCCWJ-DepPara と同じ）で、京大コーパスのものではない。学習データが UD Japanese-GSD で、文節の境界を持ち、モデルを公開できるライセンスである。#1417
並列は京大コーパスと CaboCha の形にする。並列の各要素は次の要素に係り、係りの種類は P。UD は後ろの要素を最初の要素に付け、係りが左を向く。解析器はその形を作れない。#1417、#1419
最初のモデルは IPADIC 用で、UniDic が続く。モデルは 1 つの辞書に属する。モデルは、辞書の品詞の列と分かち書きに依存する。CaboCha と J.DepP の基準を IPADIC で測ったので、数字を比べられる。#1417
Lindera の 3 つの UniDic の辞書（unidic・unidic-cwj・unidic-csj）のそれぞれにモデルを作る。スキーマは 1 つ。3 つの辞書は、分かち書きと品詞が同じではない。GSD train の文のうち、2 つの辞書で全部の形態素とその品詞が一致する文は 63〜73% である。モデルは、辞書の名前で照合する。スキーマが読む列は、3 つとも同じ位置にある。#1441
文節の区切りは、B と I の 2 ラベルの条件付き確率場で、lindera-crf で学習する。CaboCha と同じ方法で、境界ごとに独立に決める J.DepP より区切りが良い（基準を参照）。#1417、#1421
区切りの推論は、重みの表に対する自前の Viterbi で行い、lindera-crf を使わない。lindera-crf の search_best_path は、辺のラベルをすべてモデルに登録しておく必要があり（&mut self）、見たことのない文に向かない。既定のビルドを依存なしに保つためでもある。#1417、#1421
解析は shift-reduce で、素性と素性の対に対する線形の二値分類器を使う。参照した実装が両方ともこの方法で、文の長さに対して線形の時間で済む。#1417
辞書について分かっていることは、スキーマという 1 つの値に、データとして置く。列の役割、機能語のパターン、記号。区切り・解析器・出力が共有する。2 つ目の辞書は 2 つ目の値で、2 つ目のコードの経路ではない。#1421、#1422
文節の主辞は CaboCha のもの（最後の内容語）で、J.DepP のものではない。索引や抽出で文節の代表にする語である。J.DepP は助動詞を主辞にすることがある。#1422
モデルは、素性を作るもの（スキーマ、列、テンプレート。解析器では素性の集合）を一緒に持つ。学習と推論が食い違わない。#1421、#1422、#1436
解析器の素性は文字列で、名前は CaboCha と同じ（SHS:、DFP0:、GCASE:、a:）。解析と学習事例を、同じ 1 つの関数で作る。CaboCha のモデルを、素性の名前を変えずに変換できる。学習の素性が、解析の素性と食い違わない。#1436
モデルがどの群の素性を使うかは、コードではなくデータ（素性の集合）にする。文節の区切りのテンプレートと同じく、コードを変えずに素性の集合を比べられる。#1436
助詞と、係った文節の素性に表層を使う機能語は、スキーマのパターンにする。解析器に、品詞の名前も列の番号も書かない。スキーマはモデルのバイト列に入る。#1436
分類器は、2 段のインターフェースの裏に置く。素性の文字列に番号を返す段と、1 回の判定の番号に点数を付ける段。CaboCha と同じく、文節の文字列を文ごとに 1 回だけ引く。重みの持ち方を、解析器を変えずに変えられる。#1436
1 つの辞書に、モデルファイルは 1 つ。辞書の名前、スキーマ（1 回だけ）、学習した部分（文節の区切り、解析器）を持つ。利用者に要るのは、辞書ごとに 1 つのファイルで、2 つではない。部分どうしでスキーマが食い違うこともない。モデルはクレートとは別の時期に公開するので、ファイルは自分の版を持つ。#1437
モデルファイルは、バイト列を持つものについて総称な型で、その場で読む。検査は、開くときの 1 回だけ。プログラムに埋め込んだバイト列、メモリに読んだファイル、呼び出し側のメモリマップが、同じコードで読める。依存は要らず、wasm32-unknown-unknown でも動く。検査の後は、何も失敗せず、panic もしない。数をポインター越しに読まないので、バイト列の境界は関係ない（#1364 の matrix.mtx と同じ）。#1437
モデルファイルの文字列の表は、並べ替えて持ち、その上にハッシュ表を持つ。文字列を、ファイルの中の位置のまま、ハッシュの時間で引ける。並べ替えてあるので、同じ文字列からは必ず同じバイト列ができる。並べ替えた文字列の二分探索だけの形も測ったが、遅い（数字を参照）。#1437
モデルの辞書は 2 つの方法で照合する。名前は、形態素の辞書を知っている呼び出し側が照合する。素性の列の数は、いつも照合する。スキーマが読む列より少ない列の形態素は、その辞書のものではありえないので、解析せずに断る。列の数が足りている別の辞書の形態素は、形からは見分けられず、名前でしか分からない。#1437
解析器は、CaboCha と同じく、ヒンジ損失のサポートベクターマシンの dual coordinate descent で学習する。コストは CaboCha の 0.0015。J.DepP と同じ passive-aggressive も選べる。交差検証で 2 つに差は無く（88.96% と 88.88%、p = 0.22）、時間も同じ。dual coordinate descent は自分で止まる。passive-aggressive は、回る回数を選ぶ必要がある。#1437
素性の対の重みは、2^22 個の重みの表に、対をハッシュで割り当てて持つ。対ごとに重みを持つ形も選べる。精度に差は無く（p = 0.60）、解析は 6 倍速く、ファイルは 6 分の 1 になる。交差検証では 2^18 以上の大きさに差が無く、その中で dev が最良なのが 2^22。#1437
ハッシュで割り当てる対の場所は、2 つの素性の文字列のハッシュから決める。モデルの中の番号からは決めない。モデルから素性を除いても、ほかの素性の対の場所が動かない。学習と推論で、番号の振り方が食い違うこともない。#1437
解析器の重みは、1 つ 1 バイトで書く。整数と尺度の積。4 バイトの重みと精度に差が無い（p = 0.86）。2 バイトの重みは出力が同じ。ファイルは 3 分の 1 になり、解析も速くなる。#1437
解析器の素性は、CaboCha の素性に 1 つの群を足す。係り元と係り先の候補の、主辞の直後の形態素。文節の主辞は、スキーマの内容語のままにする。スキーマの主辞では、CaboCha の主辞が CaboCha の素性に与えていた情報が抜ける。文節が全体として動詞か名詞か、である（利用 / し / た、読む / こと / を）。この群がそれを戻す。交差検証で 89.19%、足さないと 88.96%（p < 0.001）。出力の主辞は内容語のまま。#1437
モデルは #1420 の規則で選び、差の無いものは同じとみなす。同じとみなした設定の中では、小さいほう・速いほうを既定にする。良い設定どうしの差は、データの揺れより小さい。大きさと速さはそうではない。#1437
モデルファイルより前の、区切りだけのファイル（マジックナンバー LDCHUNK）は、もう読まない。このときクレートは未公開で、配布したモデルは無かった。読む側を残しても、読むべきファイルが無かった。#1437
学習データには主辞と機能語の位置を書かない。読む側がスキーマから計算する。規則を変えても、古い位置がファイルに残らない。#1422
設定の比較は train の交差検証で行う。dev は僅差の設定の選択に使う。test と PUD は、報告する結果にだけ使う。dev と test は小さい。90% 前後の精度の 95% 区間は、約 ±1 ポイントになる。#1420
精度の目標は、下の「目標」のとおりとする。同じデータで測った基準の数字である。#1417
トークンフィルターは、結果を Token のフィールドに書く。Token::dependency で読める。文の番号、文節の番号、係り先、文節の中での役割、スコア。Token::details と MeCab 形式の出力は変えない。詳細の末尾の 4 つの文字列の列という決定を、これに改める。詳細は、どの出力にも後ろのフィルターにも、辞書の素性のまま渡る。結果は Token::as_value に出る（スキーマより後ろの列は出なかった）。Token を構造体の式で作るコードは壊れる。Token はここから #[non_exhaustive] なので、次のフィールドでは壊れない。#1438
フィルターは lindera-analysis の dependency feature の裏に置く。kind は japanese_dependency。設定ファイルも、コマンドも、バインディングも、TokenFilterLoader::load_from_value という固定の match でフィルターを作る。分岐を 1 つ足せば全部に効く。フィルターの登録の仕組みを足すと、名前の付け方が 2 通りになる。#1438
フィルターは、括弧の外の 。、！、？ でテキストを文に分け、文節の番号を文ごとに 0 から振る。結果は文の番号を持つ。モデルは文を単位に学習している。ラティス形式も、文節の番号を文の中で振る。#1438
フィルターは、モデルの辞書とは別の辞書のトークンと、前のフィルターが消したりつないだりしたトークンを断る。どちらも、失敗せずに誤った解析になる。#1438
CaboCha が配布するモデルを、最初のリリースの後に、変換器を通して読めるようにする。そのモデルは再配布しない。素性の取り出しと復号を分けてあるのは、このためである。#1417、#1421
テキストを受けるコマンドは、このクレートのバイナリの、学習のコードを含まないビルドに置く。cli feature がコマンドを持ち、train がそこに学習を足す。lindera コマンドからの利用は、フィルターと公開の後にする。コマンドを使うだけの人に lindera-crf が入らない。lindera-cli は公開されているので、公開していないクレートに依存できない。lindera tokenize の出力形式にするには、トークンフィルターが要る。#1439
CaboCha のオプションのうち、コマンドは、ラティス形式の出力（-f1）と 3 つの入力の層（-I）を --input-layer として持つ。木・XML・CoNLL の出力、出力の層、固有表現は持たない。ラティス形式はほかの道具が読む形式で、書き出しの実装がある。入力の層は、parse と parse --chunk がしていたことを 1 つのオプションにまとめたもの。形態素だけ、文節だけを書くコマンドは別にある。#1439
コマンドは、1 文ずつ読んで、解析して、書く。解析できない最初の文で止まり、そこまでに書いた出力は残る。パイプの中で使え、メモリが入力の長さで増えない。#1439
IPADIC のモデルは MIT ライセンスで配布し、UD Japanese-GSD への謝辞と IPADIC の表示を添える。モデルが持つのは素性の名前と重みで、注釈は含まない。このプロジェクトは、これをコーパスの改変物ではないとみなす。この問いを判断した裁判例はない。立場の根拠はモデルファイルのページに書く。コードとモデルが同じライセンスなので、モデルを埋め込んだプログラムは、辞書を埋め込んだプログラムと同じように配布できる。#1440

参照した実装

ソースを読んだ内容です。CaboCha 0.69（taku910/cabocha、commit 96e100a）と J.DepP 2022-03-18。

  • 解析。 どちらも shift-reduce で解析する（Sassano 2004）。「スタックの先頭の文節は、今の文節に係るか」という二値の判断を繰り返し、線形の時間で済む。係り先は必ず右にあり、係りは交差しない、という仮定を置く。
  • 分類器。 どちらも、一次の素性と、その対に対して分類する。CaboCha の「多項式カーネルの SVM」は、学習でも推論でも、素性と素性の対に対する線形のモデルに展開されている。
  • 文節の区切り。 CaboCha は CRF（CRF++、ラベルは B と I）で区切る。形態素ごとに 2 列を使う。正規化した表層と、品詞の階層を - でつないだものである。J.DepP は、形態素の境界ごとに独立に決める。CaboCha では、先頭の形態素は必ず文節を始める。
  • 主辞と機能語（src/selector.cpp、src/selector_pat.h）。findHead は、どちらも文節の先頭の形態素から始め、左から見ていく。素性の文字列が機能語のパターンで始まれば機能語の位置を、主辞のパターンのどれでも始まらなければ主辞の位置を書き換える。IPA と UniDic では、主辞が機能語より後ろなら、機能語を主辞にそろえる。IPA の機能語のパターンは 助詞、助動詞、動詞,非自立、動詞,接尾、形容詞,非自立、形容詞,接尾 で、これらと 記号 は主辞にならない。
  • 句読点と括弧は、正規化した表層で照合する。対象は、句点（。）と読点（、）、開き括弧 10 個、閉じ括弧 10 個である。
  • 評価（src/eval.cpp）。区切りは、始まりと長さが同じ文節についての精度・再現率・F。係り受けの精度は、区切りが正解と同じ文について、3 つのレベルで数える。すべての文節、各文の最後を除いた文節、最後の 2 つを除いた文節である。
  • 投影（tools/kc2cabocha.pl）。CaboCha の IPA のモデルは、京大コーパスを IPADIC で解析し直して学習している。文節を文字の位置で新しい形態素に合わせ、境界が形態素の途中に来たら文節をつなぐ。
  • CaboCha は、活用形を「品詞の階層の数 + 1」の列から読む。UniDic ではそこが品詞の 4 列目なので、CaboCha の UniDic のモデルは活用形を持っていない。ここでは、列の番号を写さず、辞書ごとに明示する。

できている部分と、その形の理由

型とラティス形式（#1418）

  • Morpheme は trait で、表層と、番号で引く素性の列を持つ。Sentence は形態素と Bunsetsu を持ち、文節ごとに、係り先、係りの種類（D、P、A、I）、主辞と機能語の位置、スコアがある。
  • CaboCha のラティス形式（cabocha -f1）を読み書きする。CaboCha と J.DepP のツールがやり取りする形式だからである。係りの種類は保持する（CaboCha は読むときに捨てる）。
  • Sentence::violations は、文が、解析器の仮定する木でない点を報告する。根は 1 つで最後の文節、係り先はすべて右、係りは交差しない。コーパスの変換と評価が共有する。

学習データ（#1419）

lindera-dependency convert は、UD Japanese-GSD と UD Japanese-PUD から、2 段階で学習データを作ります。

  1. 語の係り受けから文節の係り受けへ。 BunsetuBILabel=B の語が文節を始める。文節の外に係る語が、文節の係り先を決める。並列を戻す（a → b、b → c、c → h、種類は P）。木にならない文は落とす。
  2. 辞書の形態素への投影。 文章を、解析器を使うときと同じ、その辞書と Lindera の既定の設定で解析する。文節を文字の位置で形態素に合わせ、境界が形態素の途中に来たら、次に合う境界まで文節をつなぐ。つないだ文節は、kc2cabocha.pl と同じく、最後の文節の係り先を引き継ぐ。

コマンドは、train feature の裏の、クレート自身のバイナリのサブコマンドです（バイナリ自体は、#1439 から cli の裏にあります）。lindera-cli は公開されているので、公開していないクレートに依存できません。

評価（#1420）

lindera-dependency evaluate は、cabocha-system-eval と J.DepP と同じものを数えます。数字を並べて比べられるようにするためです。レベル 1（各文の最後を除いた文節）は J.DepP が報告する数字で、ここでも見出しの数字にします。一貫（end to end）は、正解の文節のうち各文の最後を除いたものについて、出力に同じ範囲の文節があり、その係り先が、正解の係り先と同じ範囲であるものを数えます。

2 つの出力は対にして比べ、McNemar の正確検定（二項分布、両側）を使います。カイ二乗の近似は使いません。食い違う対の数が小さいためです。lindera-dependency split は、交差検証の分割を「文 i は fold i mod k のテストに入る」という規則で、乱数なしで書き出すので、どこで流しても同じ分割になります。

文節の区切り（#1421）

  • 素性の取り出しと復号を分ける。 形態素からスキーマを通して列を読み、CRF++ の形式のテンプレートが素性の文字列に展開する。復号は、素性の文字列と重みの表だけを見る。後で、CaboCha と同じ文字列を作る取り出し方を足せば、同じ復号を使える。
  • 学習では、lindera-crf に、形態素ごとにラベルの数だけ辺を渡す。正解の辺を最初に置き、先頭の形態素には B だけを置く。0 でない重みを、学習したモデルから写す。復号は、search_best_path と同じ順で足し、同点も同じように扱う。dev と test のすべての文で、同じラベルを出す。
  • 既定の設定は、train の 10 分割の交差検証で選んだ。表層、品詞、活用形の 3 列。CaboCha のテンプレートに、活用形の 5 行を足したもの。L1 で係数 0.5。最良の設定と有意差のない設定のうち、最小のものである。活用形は効く。活用型は効かない。原形は、活用形に足しても何も増えない。L1 は L2 より良く、モデルは約 50 分の 1 になる。

スキーマ、主辞と機能語（#1422）

  • Schema は、品詞、活用型、活用形、原形の列の番号と、機能語のパターン、主辞にならないもののパターン、記号・読点・句点・括弧の見分け方を持つ。パターンは、品詞の階層の前方一致で、原形と、文節の中の直前の形態素のパターンを足せる。
  • Schema::positions は、CaboCha の findHead と同じ流れである。
  • 記号は、品詞に加えて表層でも見分ける。 IPADIC には半角の記号がない。, は未知語になり、名詞,サ変接続 として出る。
  • IPADIC のスキーマは、CaboCha のパターンに規則を足している。 足したのは、UD Japanese-GSD の内容の主辞との一致が裏付けるものである。する・できる を機能語にする。名詞,非自立、接尾辞の 的 と さ、助詞の直後の動詞を主辞にしない。CaboCha の規則の系統的な食い違いで最大のものは、サ変名詞 + する（利用 / し / た）で、CaboCha の規則は し を主辞にする。
  • UniDic のスキーマは 2 つ目の値で、同じ測り方で決めた。 CaboCha の UniDic のパターンに、非自立可能 を機能語として足す。主辞にならないものとして、に・と・を の直後の動詞、助動詞語幹、用言の直後の形式名詞、形容詞の直後の名詞的な接尾辞を足す。このために、区切りと解析器のコードは変えていない。表せないものが 1 つある。コーパスは数の後ろのパーセント記号を主辞にするが、UniDic はこれにほかの記号と同じ品詞（補助記号,一般）を付ける。スキーマは、記号を品詞か文字のどちらかで見分け、両方を組み合わせては見分けない。
  • 機能語は、スキーマだけで定義する。UD Japanese-GSD には、同じ意味の印がない。GSD の SYN_HEAD は、「記号でない最後の形態素」とも「主辞の次の形態素」とも一致しない。

解析器（#1436）

  • ループは、CaboCha の parseShiftReduce、J.DepP の _parseLinear と同じです。係り先の無い文節をスタックに持ち、続く文節を 1 つずつ係り先の候補にし、スタックの先頭を係り元にします。最後の文節への係りは尋ねません。ループは判定を関数として受け取るので、分類器でも文の正解でも、同じコードが動きます。
  • 素性は CaboCha のもの（src/selector.cpp、src/dep.cpp）で、7 つの群に分けています。距離、係り元、係り先の候補、係り元の前の文節、係り先の候補の後の文節、すでに係った文節、間です。文節ごとに 1 回作り、判定のときに組み合わせます。文字列を何に変えるかについて総称にしてあり、解析では分類器の番号、学習事例では文字列そのものです。
  • CaboCha との違い: 表層を正規化せず、句読点と括弧はスキーマのものを使う。主辞と機能語は #1422 のスキーマのものを使う。係り先が分からない文節は扱わない。尋ねない係りの点数は 0 にする（CaboCha は、直前の判定の点数を書く）。
  • J.DepP の素性（jdepp/pdep.cc）は違います。4 つの文節を、最初の形態素・主辞・末尾・最後の形態素で表す。2 つの主辞の表層が同じかどうか。括弧の釣り合い。間の文節のうち、係り先の候補を取り合う文節の助詞。すでに係った文節の素性は無い。J.DepP にしか無い素性は、試していません。目標に、それ無しで届いたためです。
  • LinearClassifier は、バイアス、素性の重み、素性の対の重みを、ハッシュ表から足します。手で作った重みで解析するための最小の実装です。学習したモデルは、自分の持ち方を持ちます（下を参照）。
  • 学習事例は、正解に答えさせたときにループが尋ねる判定で、それぞれが素性と答えを持ちます。CaboCha の学習モードと同じです。学習データのどの文でも、正解に答えさせると木が戻ります。

モデルファイル（#1437）

  • 1 つの辞書に 1 つのファイル。 マジックナンバーと版で始まり、辞書の名前、スキーマ、部分の一覧、部分が続きます。最初の部分は文節の区切りで、2 つ目が解析器になります。部分は省けます。train-chunker は、区切りだけのファイルを書きます。
  • その場で読む。 Model<B> は、B: AsRef<[u8]> なら何でも持ちます。バイト列のほかに持つのは、小さくて構造のあるものだけです。名前、スキーマ、区切りの列とテンプレート、9 個の遷移の重み、表の位置です。素性の文字列の重みはバイト列の中に置いたまま、from_le_bytes で読みます。
  • 検査は 1 回。 Model::new は、すべての欄、すべての位置、すべての文字列を読み、どの文字列も枠から引けることを確かめます。その後の読み取りは、範囲を確かめるスライスを通るので、できあがったモデルは panic しません。これは、ファイルのバイトを 1 つずつ変えるテストで守っています。
  • 区切りは、トレイト（ChunkerData）を通して読む。 解析器が分類器を読むのと同じ分け方です。学習の結果であるメモリ上のモデルと、ファイルの部分は、その 2 つの実装で、復号は同じコードです。dev・test・PUD のすべての文で、同じラベルになります。
  • 文字列の表は、解析器が素性の番号のために共有する部品です。並べ替えてあり、枠を持ちます。枠は、文字列の 64 ビットの FNV-1a による、開番地法のハッシュ表で、1 つの文字列に 2 つ以上の枠があります。1 つの文の素性の文字列の大半は、モデルに入っていません（L1 で残るのは 4,325 個）。そのため、効くのは「無い」と分かるまでの速さです。枠の埋まり方を半分以下にしてあるので、探索は 1〜2 歩で空の枠に当たって終わります。
  • Chunker::chunk と Parser::parse は、エラーを返すようになりました。スキーマが読む列より少ない列の形態素に対してです。これまでは、そうした形態素を、空の列として解析していました。
  • していないこと: 区切りの量子化（重みは f64 のまま。lindera-crf と同じラベルを出すためで、区切りはモデルファイルの 4% である）、チェックサム。途中で切れたファイルは長さで分かりますが、書き換わった重みは分かりません。

解析器の学習と、モデルファイルの解析器の部分（#1437）

  • 1 つの空間に、2 つのアルゴリズム。 参照した 2 つの学習器は、同じ線形のモデルを学習します。バイアス、素性ごとの重み、対ごとの重みで、カーネル (1 + s)^2 を展開した形です。刻み d は、それぞれに d、3 d、2 d を足します。CaboCha も、カーネルの問題をカーネルのまま解いてはいません（src/svm_learn.cpp）。ここの 2 つのアルゴリズムは、刻みの決め方だけが違います。対の重みをどこに置くかは、その両方の下にある 1 つの関数です。
  • dual coordinate descent は、CaboCha の solveParameters に従います。ヒンジ損失、コストによる上限、shrinking、毎回の乱数の順、射影勾配の幅 0.1 での停止です。判定の自分自身とのカーネルは、その判定の複数の対が同じ場所に当たるとき、その数の 2 乗で数えます。これで、対をハッシュで割り当てても刻みが正確になります。順は、クレートが持つ生成器（SplitMix64）と種から決まるので、同じデータからは同じモデルができます。
  • passive-aggressive は、opal に従います（PA-I）。刻みは、損失を素性の数で割った値で、コストを上限にします。対があると、1 つの刻みは点数を、素性の数の倍ほど動かしすぎます。そのため、コストが上限として効いていなければなりません。良いコストは 0.0005 の近くで、CaboCha の 0.0015 より小さい値です。重みの平均は、opal と同じ持ち方です。
  • 学習は、分ではなく秒で終わる: 66,000 件の判定は、平均 37 個の素性を持ち、対は 1 件あたり約 680 個です。1 回りで、それぞれに 1 回ずつ触ります。train の全部を、1 コアで約 3 秒で学習します。
  • ファイルの解析器の部分は、素性の集合、バイアス、量子化の尺度、素性の文字列の表とその重み、対の重みを持ちます。対の重みは、2^bits 個の重みの表か、素性ごとに相手の素性の順に並べた対です。ファイルの分類器は、これらをその場で読みます。4 バイトの重みなら、メモリ上のモデルと最後のビットまで同じ点数になります。
  • 対ごとの重みは、ここでの持ち方では遅い: 判定の対を 1 つずつ、片方の素性の対の中から二分探索で引きます。CaboCha は、頻度の上位 3,000 素性の対を三角形の配列に、残りを double array に持ちます。それは作っていません。ハッシュで同じ精度が出るためです。
  • スキーマの主辞と素性。 #1422 の内容語の主辞は、索引に使う語としては良く、解析に使う語としては劣ります。CaboCha の主辞の規則と CaboCha の素性では、交差検証が 89.22% です。スキーマの主辞では 88.96% です。主辞の直後の形態素がこの差を戻し（89.19%）、それを足すと 2 つの規則に差は無くなります。
  • train-parser --chunker は、ほかのファイルの区切りの部分を、バイト列のまま写します（ModelBuilder::from_model）。区切りと解析器を別々に学習して、1 つのファイルにまとめられます。

コマンド（#1439）

  • parse は、利用者のコマンドです。1 行 1 文のテキストを受けて、ラティス形式で書き出します。これまでは、evaluate のためにラティス形式のファイルを解析するサブコマンドでした。テキスト用のサブコマンドを別に足すと、同じ解析に入口が 2 つできます。これまでの動きは、--input-layer bunsetsu と --input-layer morphemes です。
  • テキストは、学習データと同じ設定で分かち書きします。Mode::Normal で、ユーザー辞書は使いません。convert と同じ設定です。違う分かち書きは、モデルが学習したものではなくなります。
  • 読み込んだ辞書の名前を、モデルファイルの名前と比べます（#1437 の Model::check_dictionary）。モデルファイルに名前を持たせたのは、この照合のためです。ラティス形式の入力では辞書が無いので、素性の列の数だけを検査します。
  • feature を 2 つに分けました。cli は clap と lindera-segmenter を、train はそこに lindera-crf と serde_json を入れます。scripts/check_dependency_crate.sh が、cli のビルドに lindera-crf が入らないことを検査し、CI のジョブが、そのビルドでコマンドをテストします。
  • DictionaryMorpheme（トークンから作る形態素）を、train の裏の corpus モジュールから、既定のビルドへ移しました。
  • 未検証: CaboCha の道具で出力を読むこと。ここではビルドしていません（#1433）。出力は、lattice::parse と evaluate で読めることを確かめています。

トークンフィルター（#1438）

  • match の分岐 1 つが、どこからでもフィルターを作ります。 設定ファイル、lindera コマンド、バインディングが呼ぶのは TokenFilterLoader::load_from_value です。分岐は dependency feature を付けたときにあり、付けていないビルドでは、別の分岐がその kind を断って feature の名前を示します。何もしなければ、そのようなフィルターは知らない、というエラーになるところです。scripts/check_dependency_crate.sh が、feature を付けていないビルドにこのクレートが入らないことを検査します。
  • Token のフィールドは、値を cold な関数で解放する枠です。 ふつうの Option<Box<_>> のフィールドにすると、トークンを破棄する箇所で破棄の処理がインライン展開されなくなり、フィルターを使わない分かち書きの命令数が、IPADIC で 0.73% 増えました。枠は、値の有無だけをその場で調べ、残りを関数に回します。15 の計測で、増加は最大 0.35% です。トークンは、ポインタ 1 つ分だけ大きくなります。
  • 半角のピリオドでは、文を終えません。 スキーマの句点は 。、．、. です。これをそのまま使うと、UD Japanese-GSD の test の 543 行のうち 4 行が分かれ、どれも数（4.20、1.5km）か ... の位置でした。全角の ． は、直後が数字でなければ文を終えます。！ と ？ でも終えます。IPADIC では、これらは句点ではなく記号です。
  • 前のフィルターについてこのフィルターに見えるのは、位置です。 トークナイザーは、トークンに 0 から隙間なく位置を振ります。トークンを消すフィルターは隙間を残し、つなぐフィルターは位置を 2 つ以上占めるトークンを残します。書き換えられた表層や詳細と、末尾から消されたトークンは見えません。文書では、このフィルターを最初に置くよう案内しています。
  • トークンは、その場で読みます。 フィルターの形態素は、トークンの表層と詳細を借ります。モデルは Arc の中にあり、フィルターの複製の間で共有します。トークナイザーを複製すると、フィルターも複製されます。
  • フィルターの結果は、コマンドの結果と同じです。 UD Japanese-GSD の test の 543 文で、すべてのトークンの文節、係り先、役割、スコアが、同じモデルの lindera-dependency parse と一致します。
  • バインディングは、係り受けをトークンの上の独立したオブジェクトとして返します。 フィルターを使わなければ何も返しません。Python では None、Ruby では nil、PHP では null で、Node.js と WebAssembly ではプロパティがありません。この 2 つではトークンがプレーンなオブジェクトなので、これまでと同じオブジェクトのままです。最後の文節の係り先は、コマンドの JSON と同じく、どのバインディングでも null です。lindera-binding の TokenView が、5 つすべてに運びます。
  • Node.js は、6 つのプロパティの名前を、係り受けを持つ最初のトークンで作ります。 そのトークンを作るハンドルスコープの中で作り、スコープを開き直した後は作り直します。フィルターを使わない呼び出しは、これまでと同じ呼び出しで、これまでと同じオブジェクトを作ります。
  • WebAssembly は、appendDependencyFilter でモデルのバイト列を受け取ります。 読めるパスが無いためです。そのために、lindera-binding のビルダーは Rust で作ったフィルターを受け取り、kind で足したフィルターの間の、足された位置で動かします。
  • 未検証: IPADIC 以外の辞書。スキーマがまだありません。
