Lindera ドキュメント

CaboCha のモデル

CaboCha には、京都大学テキストコーパス 4.0 で学習したモデルが付属しています。コーパスが無いと学習し直せません。また、文節の基準は京大コーパスのもので、このクレートのモデルが従う UD Japanese-GSD のものとは違います。lindera-dependency convert-cabocha は、そのモデルをモデルファイルに変換します。変換したモデルでの解析は、CaboCha の解析と同じ結果になります。

モデルの利用条件

変換したモデルの利用は、元のモデルと同じく、研究目的と個人利用に限られます。ご自身が入手した CaboCha のファイルを変換し、結果を配布しないでください。 このクレートとそのリリース、ビルドは、CaboCha のモデルを含みません。

CaboCha のライセンス（LGPL または BSD ライセンス）は、モデルには及びません。CaboCha の配布ページには、次のように書かれています。

付属のモデルファイル(model 以下のファイル)にはBSDライセンス は適用されません。BSDライセンス は, 付属のプログラムや学習ツールのソース・コード, ドキュメントのみに適用されます。

付属のモデルファイルは, 株式会社毎日新聞社の御厚意により 配布されている毎日新聞記事CD-ROM版を基に学習, 作成されたものです。付属のモデルファイルは, 毎日新聞データ使用許諾に関する覚書に記載の利用条件内で その使用及び, 複製，改変，頒布が認められます. そのため配布しているモデルをそのままの形で使うことは, 研究目的, 個人利用に限られます.

つまり、BSD ライセンスが及ぶのは、プログラム、学習ツール、ドキュメントだけです。モデルは毎日新聞記事 CD-ROM 版から作られたもので、そのデータの使用許諾の覚書の条件の範囲で、使用・複製・改変・頒布が認められます。そのため、配布のモデルをそのまま使うことは、研究目的と個人利用に限られます。ご自身のコーパスで学習したモデルには、この制限はありません。学習の方法は、文節の区切りと係り受けの解析を見てください。

cabocha -f1 -n0 は、この文に同じ結果を書きます。違うのは 1 つの数字だけで、最後の文節への係りの点数です。この係りは判定をしません。CaboCha はそこに直前の判定の点数（-0.742128）を書き、parse は 0 を書きます。

Rust からは、lindera_dependency::cabocha::convert に 2 つのファイルの内容を渡すと、2 つのモデルと、変換で行ったことの記録が返ります。

変換するもの

区切りのモデルは、CRF++ のテキスト形式のモデルです。テンプレート、素性の文字列、重みを、そのまま区切りの部分に入れます。重みは 32 ビットの浮動小数点に丸めます。CaboCha が読むコンパイル済みのモデルで、CRF++ がそう持つためです。

解析器のモデルは、2 次のカーネルの support vector です。判定の点数は、support vector についての和 Σ α (1 + s)^2 で、s は support vector が判定と共有する素性の数です。これは、バイアス、素性ごとの重み、素性の対ごとの重みに、誤差なく展開できます。解析器の部分が持つのは、この形です。ただし、CaboCha はそのままでは解析しません。cabocha-model-index がテキストのモデルをコンパイルするときに近似します。変換は同じ手順を踏むので、判定で足し合わせる整数が CaboCha と同じになります。

  • 頻度の高い 3,000 個の素性どうしの対は、すべて残します。
  • それ以外の対は、2 件以上の support vector に現れ、重みが sigma × positives / all 以上か、-sigma × negatives / all 以下のときに残します。sigma は 0.0001 です。positives と negatives は、重みが正の support vector と負の support vector の件数、all は全件数です。
  • 重みは 32 ビットの浮動小数点で足し込み、絶対値の最大を 1,048,575 で割った値で割って、整数に切り捨てます。モデルファイルは、その整数を量子化せずに持ち、割った値を重みのスケールとして持ちます。
オプション既定
--sigma0.0001cabocha-model-index の -s
--min-support2-n
--frequent-features3000-F

既定は cabocha-model-index の既定で、CaboCha 自身のビルドは、これで付属のモデルをコンパイルします。--sigma 0 --min-support 1 はすべての対を残します。これはカーネルそのもので、CaboCha が解析に使うものではありません。

残る対重みのある対ファイル変換の時間

素性を作るものは、モデルファイルのデータです。変換したモデルでは、CaboCha のものになります。

  • 表層は、素性にする前と、記号として照合する前に、CaboCha の表で正規化します。半角カナは全角に、全角の英字・数字・記号は ASCII になります（ＡＢＣ は ABC、ｶﾞ は ガ）。
  • 機能語は、助詞、助動詞、動詞,非自立、動詞,接尾、形容詞,非自立、形容詞,接尾です。主辞は、そのどれでもなく記号でもない、最後の形態素です。このクレートの ipadic のスキーマとは違います。そちらはパターンが多く（主辞と機能語）、利用 / し / た の主辞は、ここでは し、そちらでは 利用 です。
  • 句読点は 。 と 、、括弧は CaboCha のもので、どれも表層の全体で照合します。

CaboCha との一致

scripts/dependency/cabocha_models.sh は、IPA のモデルを変換し、同じ入力を、CaboCha 0.69（96e100a。scripts/dependency/build_baselines.sh でビルドし、モデルは CaboCha 自身のビルドがコンパイルしたもの）と、変換したモデルを使う lindera-dependency parse に渡します。入力は、UD Japanese-GSD と UD Japanese-PUD の 9,066 文です。決まったテキストとして使うだけで、その正解は使いません。

同じ形態素（Lindera と IPADIC のもの）を渡すと、すべてが一致します。

テキストからの場合、CaboCha は MeCab と mecab-ipadic で、parse は Lindera とその IPADIC（mecab-ipadic のソースから作ったもの）で形態素にします。2 つの形態素が同じになる文は 91%〜98% で、その文の解析は同じです。

残りの文は、形態素の切り方が違います。そのほとんどは、辞書に無いカタカナの語のところです（PUD と GSD train で 335 文のうち 332 文）。MeCab は コリ・シューマン を 1 語にし、Lindera は 3 語にします。MeCab が メトロ / ポリ / タン と切るところを、Lindera は メトロポリタン にします。これはトークナイザーの違いで、モデルの違いではありません。

制限

  • 速さ。GSD train の 7,024 文を形態素から解析するのに、parse は 3.03 秒、CaboCha は 0.92 秒かかります。変換したモデルは、対ごとに重みを持ちます。このクレートのモデルは、対を表にハッシュします。そちらの速さはモデルファイルを見てください。
  • 最後の文節への係りの点数は 0 です。このクレートのどのモデルでも同じです。
  • 長い文節。CaboCha は、1 つの文節について、素性を 128 個、素性の文字列を 2,048 バイトまでしか持ちません。このクレートはすべて持ちます。上のテキストの 76,659 文節は、最大でも 40 個・882 バイトで、上限に届きません。上限を超える文節では、結果が違いえます。
  • 区切り。このクレートは、B で始まる最良の経路を探します。CaboCha は、最良の経路を取ってから、最初の形態素を文節の始まりにします。また、CRF++ は 1 つの形態素の重みを 32 ビットの浮動小数点で足し、このクレートは 64 ビットで足します。どちらも、上のテキストの文節を変えませんでした。
  • 精度。CaboCha のモデルの精度は、ここでは測っていません。京大コーパスが手元に無く、UD Japanese-GSD での精度は、文節の 2 つの基準を比べることになるためです。
  • 未検証: Linux（x86_64）の GCC 15.2 以外のコンパイラ・OS でビルドした CaboCha。
